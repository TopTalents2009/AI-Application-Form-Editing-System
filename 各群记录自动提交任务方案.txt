各群记录自动提交任务方案
（先不开发，仅存档。2026-09-21）

说明
  目标：模型根据企业微信群里的申报书与修改意见，自动提交修改任务。
  原则：不要让模型一直盯着整群聊天。解析服务已经在写库，本系统做
        增量扫描 → 规则初判 → 小窗口让 Gemini 配意见 → 过门槛才建任务。
  现成能力：主界面 / 后台「各群记录」里的「拆解任务」已覆盖后半段
        （识别、配意见、下载附件、runner.create）。差的是值班进程和自动放行门槛。
  底线：任务停在「待确认计划」，不要自动点「确认写入」。
        群文件名经常不准（例如聊天里叫「杜垚.pdf」，缓存里是意向协议）。


一、目标链路

  企业微信 PC 库
    → 解析服务 :8767（各电脑心跳入库）
    → 本系统值班进程（每 1～3 分钟扫关注群的新消息）
    → 规则识别申报书 / 忽略合同、协议、统计表
    → 等附件缓存齐 + 等修改意见窗口
    → Gemini 只看这一案附近几十条消息（可再抽 PDF 首页做复核）
    → runner.create + enqueue（与现在拆解上传同一条路）
    → 任务列表出现「待确认」，人审计划后再写入

  「实时」指分钟级跟上群里新文件，不是把全文流进模型。


二、为什么不能「模型实时读聊天」

  做法                              问题
  --------------------------------  ------------------------------------------
  每条新消息都丢给 Gemini           贵、慢、把「收到/好的」当意见
  把整群历史塞进上下文              超窗、配错人、重复建任务
  只看文件名就上传                  已发生：短名 PDF 实际是意向协议
  文件未缓存就提交                  拆解会报未缓存，任务空跑
  自动确认写入                      错文件会直接改申报书

  模型只做两件事：
    1）确认这是不是申报书
    2）这段意见属于哪一本案
  文件二进制仍走现有下载与 runner。


三、建议实现（复用现有代码）

  后台已有配置 wecomChat.groups（关注群）。再加一块自动提交配置即可，例如：
    - 总开关
    - 值班账号（任务归属）
    - 扫描间隔
    - 意见等待窗（建议 30～90 分钟；与现有 48 小时聚类窗分开：
      等待窗用于「先有书、后有意见」）
    - 置信度：auto / review / off
    - 是否允许「只有申报书、群里还没有意见」（走书内批注）

  1. 值班进程

     FastAPI 启动后跑一个 asyncio 循环（不要做在浏览器里）：

     1）health 不通就跳过。
     2）list_merged_groups，只处理关注群。
     3）每个群记下 cursor：last_message_id + last_time
        （文件即可，如 data/wecom_watch.json）。
     4）拉 cursor 之后的新消息；为了配意见，每次回看 48 小时
        （与现在 cluster_messages 一致）。
     5）调用现有 cluster_messages → assist_split_with_gemini
        → annotate_existing。
     6）对通过门槛、且尚未建过 wecom.caseId 的案，走现在的
        split-create 逻辑（下载附件、resolve_app_upload、runner.create）。

     幂等已经有半套：caseId 是 session + message_id + 文件名的哈希，
     annotate_existing 能挡住重复建。自动模式遇到 existing 直接跳过，
     不要用「重新上传」。

  2. 自动放行门槛（必须比人手点拆解更严）

     同时满足才 auto 提交：

     1）规则认为是申报书：文件名含申报书/申请表，或「人名.pdf」
        且未命中意向协议/合同/统计表等排除项
        （现有 classify_file / resolve_app_upload）。
     2）附件已缓存：ready 为真；未缓存则进重试队列，最多等数小时
        （解析端电脑还没落到本地）。
     3）内容抽检（建议第一期就做）：下载后读 PDF 前 1～2 页或 Word 标题，
        命中「意向协议 / 劳动合同 / 承诺书」则拒绝。
        这能挡住「聊天名是人名、缓存却是协议」这类错。
     4）意见：有意见文档或群聊修改意见；若选择允许无意见，
        则只建「读申报书批注」的任务，并在任务上打标。
     5）Gemini 与规则一致：规则判 ignore、模型判 app 时，
        放入「待人审」列表，不要自动传。
     6）已有高相似任务：locate_tasks 高置信则跳过。

     其余一律进主界面各群记录旁的「自动发现、待确认拆解」，人再点上传。

  3. 意见怎么「实时」挂上

     群里常见顺序是：先发书，过一会儿才说改哪几项。

     - 发现申报书后先暂存案，不立刻建任务。
     - 等待窗内若出现意见文档或意见文本，再提交。
     - 超时仍无意见：按配置要么只交书，要么留在待审。
     - 任务已建、后来又来了意见：第一期不要自动追加到运行中任务
       （容易打乱计划）；标「有新意见」让人重新拆或开新任务。

  4. 主界面怎么呈现

     各群记录里加一条状态即可，不必新页面：
     - 自动已提交 → 任务列表里出现，来源 wecom
     - 等缓存 / 等意见 → 文件卡片上显示原因
     - 规则与模型不一致 → 「待确认拆解」

     开关放管理后台，和现有「关注群」在一起。


四、分步落地

  第一期（就能用）
    值班轮询 + cursor + 复用拆解上传 + 未缓存重试 + 重复跳过
    + 停在待确认计划。
    先只处理关注群、且规则高确信的申报书。

  第二期（降错传）
    下载后内容抽检；规则/模型冲突进待审；等意见窗口。

  第三期（可选）
    解析服务若能推「新消息」再改推送，去掉空转轮询；
    企微通知「已出计划请确认」。


五、明确不要做的

  - 不要自动「确认写入」。
  - 不要对已有任务默认重新上传。
  - 不要让模型读未下载的附件「脑补」内容。
  - 不要扫描全部会话；只扫配置的关注群。
